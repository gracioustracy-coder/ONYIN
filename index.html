About Me

A Different Kind of Automation Professional

My path into automation started somewhere most technical professionals wouldn't expect — inside spreadsheets, ledgers, and financial reports.

With a background in accounting, I spent years working with structured business processes: tracking records, ensuring accuracy, understanding business logic, and spotting where things break down. I learned to think in systems — inputs, transformations, outputs, controls.

What I discovered is that those same principles are exactly what good automation requires. A workflow without business logic is just noise. A system without error handling is unreliable. A process that isn't grounded in the actual business problem will never be built correctly.

So rather than leaving accounting behind, I expanded it. I've been building practical automation systems using n8n and Zapier, integrating AI via OpenAI, working with data tools like Airtable, and designing multi-step workflows that solve real operational problems.

The projects in this portfolio are not tutorials I followed. They are systems I designed, built, debugged, and tested — including tracing a data integrity failure that was silently overwriting 25+ records, and designing an AI pipeline with a deliberate human-review checkpoint because some decisions should never be fully automated.

I am developing professionally and I am honest about that. What I bring is a combination that is genuinely uncommon: business process understanding, automation capability, and the discipline to care about reliability.

01

Gym Membership Management System

n8n · Airtable · Gmail · Fillout · 3 integrated sub-workflows

The Business Problem

Small gyms typically track memberships manually — spreadsheets, handwritten notes, or nothing at all. This creates predictable failures: members are not notified when their membership is approaching expiry, renewals are missed, and the owner spends time on administrative tasks that should be automated.

The goal was to build an end-to-end automated system covering the full membership lifecycle without requiring the gym owner to manage anything manually day-to-day.

The Solution

Three separate but connected n8n workflows, all reading from and writing to one shared Airtable database. Each sub-workflow handles a distinct phase of the membership lifecycle.

1A
Onboarding

Fillout signup form → Webhook → Code node calculates expiry date using calendar-accurate month math → Airtable creates member record → Gmail sends welcome email with plan, start date, and expiry date.

1B
Expiry Reminder

Daily schedule trigger → Retrieve all member records → Code node calculates days remaining per member → Branch: if 2 days remaining, alert gym owner; otherwise send daily "no action needed" confirmation.

1C
Renewal

Renewal form submission → Search for existing member by email → If found: recalculate dates, update existing record, send confirmation. If not found: alert admin immediately. No duplicates created.

Key Technical Decisions

  • Calendar-accurate date math: Used JavaScript's setMonth() rather than fixed day counts (e.g., "30 days for monthly"). This correctly handles months of different lengths and avoids expiry date errors at month boundaries.
  • Single shared Airtable base: All three workflows read from and write to the same member table — no duplicate tables per workflow. This keeps member data consistent and eliminates synchronisation issues between stages.
  • Search-before-update on renewals: The renewal workflow always searches for the existing member first, rather than creating a new record. This prevents duplicate membership entries regardless of how many times a member renews.
  • Normalised search result output: A dedicated Code node guarantees exactly one output item from the Airtable search, regardless of whether zero or multiple records match. This prevents the pipeline from silently skipping the branch logic on no-match.
  • No silent failure paths: Every failure case — no matching member on renewal, expired membership — routes to an admin alert rather than doing nothing.

Challenges & How I Solved Them

Critical Data Integrity Issue

During testing of the renewal workflow, I identified a filtering issue that was causing the Airtable search node to return and subsequently update all records in the database rather than just the matching member. I traced the issue to a malformed filter formula — the field comparison condition was missing, leaving only a raw value. I corrected the formula to a proper Airtable field comparison, manually cleaned the affected test records, and retested the workflow from a clean state to confirm the issue was fully resolved.

Webhook Payload Mismatch

The actual field names sent by Fillout's webhook differed from what I initially assumed — the email field arrived as emailAddress rather than email, and the photo URL as profilePhotoUrl rather than photoUrl. I inspected the live payload, identified every mismatched field name, and updated the Code node to reference the correct keys. I also added fallback logic for the photo URL to handle inconsistent nesting across different form configurations.

Node Reference Errors Downstream

In the renewal workflow, downstream Gmail nodes were referencing the wrong node output — because Airtable's Update node response overwrites the default $json context. I corrected the expressions to explicitly reference the calculation node by name, ensuring the correct member data flowed to the confirmation email rather than the raw Airtable update response.

Webhook Path Conflict

Two workflow versions registered the same webhook URL simultaneously, causing a routing conflict where submissions were being directed to the wrong workflow. I traced the conflict to a duplicate workflow left active and deactivated it, restoring clean and predictable webhook routing.

Result & Value

The completed system eliminates all manual membership administration for the gym. New members are onboarded and welcomed automatically. Approaching expirations are flagged to the owner daily without manual checking. Renewals are processed, records updated, and confirmations sent without staff involvement. Every failure path notifies a human rather than silently failing. The gym owner's only required action is reviewing admin alerts when they arrive.

02

AI-Powered Supplier Quote Assistant

n8n · OpenAI · Gmail · Airtable · Capstone Project

The Business Problem

Businesses that handle supplier or procurement enquiries by email face a recurring manual task: reading each incoming request, extracting the relevant information (what's needed, quantity, deadline, who sent it), logging it for tracking, and drafting a professional response. Done manually, this is time-consuming and inconsistent.

The challenge with automating this is that the inputs are unstructured. Unlike a form, an email can say anything. Extracting reliable structured data from free-form text is exactly where AI is genuinely useful — and exactly where it needs to be handled carefully.

The Solution

A five-stage n8n workflow that handles the complete journey from incoming email to a reviewable draft response, with a deliberate human checkpoint before anything is sent.

1
Email Detection

Gmail Trigger monitors the inbox for new incoming emails and passes the email body into the pipeline.

2
AI Extraction

OpenAI reads the email body and extracts: requester name, email address, company name, items requested (with quantities), and deadline — returning strict JSON output.

3
Parsing & Safety Layer

Code node parses AI output with try/catch error handling, strips any markdown formatting artifacts, and applies fallback logic for missing fields — ensuring no malformed AI output crashes the pipeline.

4
Airtable Logging

Structured extracted data is logged to Airtable for tracking and follow-up — creating an audit trail of every incoming request.

5
Draft Generation & Human Review

A second OpenAI call generates a professional reply using extracted data and explicit price placeholders. Saved to Gmail Drafts — never sent automatically. Human approval required before any response reaches a customer.

AI Design Decisions

  • Two separate OpenAI calls with distinct roles: The first is focused purely on structured extraction — it returns JSON. The second generates natural language — it produces a readable email draft. Combining them into one call would compromise both tasks.
  • Price placeholders enforced: The AI is explicitly instructed to use [INSERT PRICE] placeholders rather than generate or estimate pricing. This is a deliberate design boundary — the AI assists with communication, not commercial decisions.
  • Gmail trigger over a form: The system is designed to process unstructured email text. Using a form would have structured the input in advance, defeating the entire purpose of the AI extraction stage.

Human-in-the-Loop Design

The most important design decision in this project is what the workflow deliberately does not do.

The final Gmail node is configured as "Create Draft" — not "Send". This is enforced at the technical level. The AI-generated response never reaches a customer without a human reviewing and approving it.

Pricing, commitments, and customer relationships should not be delegated to an automated system without oversight. The workflow handles the time-consuming parts — reading, extracting, structuring, and drafting — while keeping the human responsible for what actually gets sent.

Challenges & How I Solved Them

Discovering the Actual AI Output Path

The OpenAI Responses API returns output in a different structure than the standard Chat Completions API. I initially referenced the wrong path, which returned undefined values downstream. I inspected the live raw JSON output from the node, identified the correct nested path (output[0].content[0].text), and updated all extraction expressions accordingly.

Building Defensive Parsing for AI Output

AI output is not always perfectly formatted. OpenAI sometimes wraps JSON responses in markdown code fences, which breaks standard JSON.parse(). I built a parsing step that strips those fences before parsing, uses try/catch to catch remaining errors, and flags malformed responses with a debug field — ensuring no inconsistent AI output ever crashes the pipeline silently.

Handling Missing Data Gracefully

During testing with a real email that lacked a sender signature, the AI correctly returned null for the requester name — confirming the extraction logic was working as designed. I added fallback logic (parsed.requesterName || parsed.requesterEmail?.split('@')[0] || 'Unknown') to use the email prefix when no name is available, preventing null-value errors from propagating downstream.

Node Reference Errors in Final Stage

The final Gmail draft node referenced node names that had changed during the build process, causing "Referenced node doesn't exist" errors. I identified every affected expression, confirmed the exact node names in the workflow canvas, and corrected all references — then verified the updated expressions resolved correctly before retesting end-to-end.

Result & Value

The workflow reduces the manual effort of processing each supplier enquiry from minutes to seconds — while preserving human review before any response is sent. The AI handles reading, extraction, logging, and drafting. The human handles approval and sends. Tested end-to-end with a real email: structured data extracted correctly, Airtable record created, Gmail draft created and confirmed via labelIds: ["DRAFT"].

My Approach

How I Think About Automation

Automation built without business understanding is just complexity for its own sake. Here is how I approach every workflow — from first conversation to final test.

01

Understand the Business Problem First

Before opening any automation tool, I want to understand what actually happens in the process today — where time is wasted, where errors occur, where data gets lost, and what a successful outcome looks like. Technology is not the starting point. The problem is.

02

Map Every Path Before Building

I identify every step, every decision point, and every failure path before writing a single node. A workflow that only handles the expected case is not ready for a real business. Error paths and edge cases are part of the design from the beginning — not additions after something breaks.

03

Design for Reliability, Not Just Functionality

A workflow that works once is not useful. I build in validation, error handling, fallback logic, and admin alerts so that when something unexpected happens, the system either recovers gracefully or notifies a human. It does not silently fail and leave no trace.

04

Know Where AI Should — and Shouldn't — Decide

AI is powerful for processing unstructured data, generating drafts, and assisting with decisions. But pricing, customer commitments, and business-critical choices should not be delegated to an automated system without oversight. I design human checkpoints deliberately, not as a fallback when automation is too complex.

05

Test Until You Actually Trust It

I test with real inputs, not just the expected ones. That means testing what happens when a field is empty, a webhook payload is structured differently than documented, a database search returns zero results, or an AI response comes back in an unexpected format. The goal is a system you can rely on — not one that works in ideal conditions only.
